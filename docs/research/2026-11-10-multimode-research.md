# Multi-mode picker research (Heltec WiFi LoRa 32 V4, 16 MB)

Date: 2026-11-10. Read-only research. Items marked UNVERIFIED were not confirmed from source and need a check before they are relied on.

## Summary of blockers
No hard blocker. Real risks: (a) RNode and Meshtastic both want the partition label "spiffs"; (b) shared "nvs" can be wiped by Arduino init errors or by Meshtastic factory reset; (c) rnodeconf and Meshtastic OTA can overwrite things outside their slot (details below); (d) the picker needs a small custom bootloader, the stock config keys cannot do "picker on every boot".

## 1. RNode firmware (Mark Qvist, GPLv3)
- Official V4 support exists. Board ID `BOARD_HELTEC32_V4` = 0x3F, product 0xC3, model 0xC8 (850-950 MHz, 28 dBm). Release assets are named for "Heltec V4PA" (`rnode_firmware_heltec32v4pa.zip`). The 1.84 release added V4; 1.86 added V4.3 and V4 LNA/GC1109 fixes. Source: Boards.h and Makefile on https://github.com/markqvist/RNode_Firmware (master), release notes via https://api.github.com/repos/markqvist/RNode_Firmware/releases/latest.
- Latest release: 1.86, published 2026-04-24.
- Note: Boards.h defines no OLED pins for V4 in the fetched text (HAS_DISPLAY true), UNVERIFIED how it drives the SSD1306. PRG is GPIO0 (`pin_btn_usr1`).
- Build: `arduino-cli`, FQBN `esp32:esp32:esp32s3:CDCOnBoot=cdc`, partition scheme `no_ota`, `-DBOARD_MODEL=0x3F`. Core `ARDUINO_ESP_CORE_VER` = 2.0.17 (IDF 4.4.7); 3.2.0 (IDF 5.4.1) is present but commented out in the Makefile.
- Flashing: `rnodeconf` (autoinstall or update) runs esptool at fixed offsets from the zip: bootloader, partition table, `boot_app0` at 0xE000, firmware at 0x10000, console image at 0x210000 (Makefile `upload-heltec32_v4`). This will overwrite our bootloader, partition table and otadata if a user runs rnodeconf against the board. Mitigation: ship the RNode image through the picker (we flash it into its own slot) and tell users not to run `rnodeconf --autoinstall` in this mode. `rnodeconf` does also set the firmware hash in the device EEPROM.
- Partition table used (arduino-esp32 2.0.17 `no_ota.csv`): nvs 0x9000/0x5000, otadata 0xE000/0x2000, app0 (ota_0) 0x10000/0x200000, spiffs 0x210000/0x1E0000, coredump 0x3F0000/0x10000. Console image is a SPIFFS image of 1966080 bytes.
- Storage: ESP32 uses the Arduino `EEPROM` library, which in core 2.0.17 is NVS backed: `nvs_open("eeprom")` and blob key `"eeprom"` in the default NVS partition (EEPROM.cpp 2.0.17). Size 1024 bytes, `CONFIG_OFFSET` 0. Holds provisioning (product/model/hwrev, checksum MD5, lock byte) and radio config. Wiping NVS destroys RNode provisioning (it can be re-provisioned with rnodeconf).
- Offset and signature checks: `device_validate_partitions()` (Device.h) hashes the bootloader (ESP_BOOTLOADER_OFFSET..), partition table, and the firmware via `esp_partition_get_sha256(esp_ota_get_running_partition(), ...)`. Only the firmware hash is compared (against the EEPROM stored target, when `VALIDATE_FIRMWARE` is on). The hash is of the image content of the running partition, not its offset, so running from another ota_N slot is fine as long as the image is bit-identical to the released one. Bootloader and partition table hashes are computed and reported but not compared. A mismatch of firmware hash makes `device_init()` fail, so never repack or patch the RNode image.
- It does not mark itself valid or use esp_ota; no OTA in this scheme.

## 2. Meshtastic (GPLv3)
- Target name: `heltec-v4` (OLED, `HELTEC_V4_OLED`, SSD1306 driver, I2C SDA 17 SCL 18, OLED reset 21, Vext 36, PRG GPIO0), also `heltec-v4-tft`. Board `heltec_v4`, 16MB scheme (`variants/esp32s3/heltec_v4/platformio.ini`). Heltec's page says the plain V4 uses "firmware-heltec-v4", V4-R8 uses a different build.
- Latest stable: v2.7.26.54e0d8d, published 2026-06-24 (GitHub releases API "latest"). Pre-releases v2.8.1 (2026-10-01) and v2.8.2 (2026-11-02, 2026-11-04) exist.
- Partition table for heltec-v4 is `default_16MB.csv` (repo root, develop): nvs 0x9000/0x5000, otadata 0xE000/0x2000, app0 ota_0 0x10000/0x640000, app1 ota_1 0x650000/0x640000, spiffs 0xC90000/0x360000, coredump 0xFF0000/0x10000. Actual app size of heltec-v4: UNVERIFIED, expect roughly 2 to 3 MB.
- Filesystem: LittleFS in the partition of subtype spiffs (manifest maps it to part name `spiffs`), mounted with the default label "spiffs". Settings/nodedb are in LittleFS, not NVS.
- NVS usage: namespace `meshtastic` (`rebootCounter`, `firmwareVersion`, `hwVendor`) via Preferences (main-esp32.cpp); `MeshtasticOTA` namespace (OTA method, 32-byte hash, WiFi SSID/PSK); NimBLE persistence enabled (`CONFIG_BT_NIMBLE_NVS_PERSIST=y`, BLE bonds in NVS). `NodeDB::factoryReset(eraseBleBonds=true)` calls `nvs_flash_erase()` ("erase what's in NVS including ssl keys, persistent variables and ble pairing"). This wipes the whole shared NVS, including RNode's EEPROM blob.
- OTA: the updater is a separate small loader image that lives in the partition of subtype `ota_1` (found with `esp_partition_find_first(APP, APP_OTA_1)` in `MeshtasticOTA.cpp`, so by subtype, not offset or label). Meshtastic calls `esp_ota_set_boot_partition(ota_1)` and reboots into the loader, which flashes the new firmware into the main slot and boots it. WiFi OTA loader is about 640 KB (repo `meshtastic/firmware-ota-wifi`, `esp32-unified-ota`). The loader validates `project_name` in the app descriptor. UNVERIFIED which partition the loader writes to. If it uses `esp_ota_get_next_update_partition`, then with more than two ota slots it picks (ota_1 + 1) = ota_2, which would overwrite another mode. Needs a read of the loader source before Meshtastic OTA is enabled. Safe default: Meshtastic OTA is not supported in this build; Meshtastic is updated only by the picker host tool.
- Looks up by subtype (ota_1) and by label ("spiffs"), not by hard-coded offsets. Works from any offset.
- Toolchain: pioarduino platform 55.03.312-1 (`variants/esp32/esp32-common.ini`). From a community version table, 55.03.3x maps to Arduino 3.3.x on IDF 5.5.x, so likely IDF 5.5. UNVERIFIED exact core. Meshtastic also uses deep sleep, so wake from deep sleep must return to the same mode (see section 4).

## 3. Simian Radar (F:\simian-radar)

No offsets in code. It does not call esp_ota or Preferences directly (grep). Setup writes only LittleFS marks.bin.

## 4. Running from non-default app partitions with an IDF 5.4.1 bootloader
- The bootloader only validates and loads an image (magic 0xE9, segment checks, SHA-256, chip id). It does not care which IDF built the app, so IDF 4.4 (Arduino 2.0.17) and IDF 5.1 to 5.5 apps boot from any `factory`, `test` or `ota_N` slot. Apps must be 64 KB aligned (0x10000).
- Watch for: `min_chip_rev` / `max_chip_rev_full` in the extended image header (5.4 bootloader checks them; 4.4 apps default to rev 0 min, fine); the bootloader (not the app header) sets flash mode/frequency/size, so build the bootloader as QIO 80 MHz 16 MB; PSRAM is quad 2 MB so the bootloader needs no PSRAM init (do not enable octal); keep `CONFIG_ESPTOOLPY_FLASHSIZE_16MB`. The app descriptor (magic 0xABCD5432) must exist for `esp_ota_set_boot_partition` and for Meshtastic's `project_name` check. Rollback (`CONFIG_APP_ROLLBACK_ENABLE`) is off in the Arduino builds here; do not enable it in the picker.
- How the bootloader chooses (bootloader_start.c, v5.4.1): `call_start_cpu0` runs `bootloader_before_init` hook, `bootloader_init()`, `bootloader_after_init` hook, then `select_partition_number()` which calls `bootloader_utility_get_selected_boot_partition()` (reads otadata, falls back to factory if otadata is invalid or blank), then applies GPIO overrides (`CONFIG_BOOTLOADER_FACTORY_RESET` with `CONFIG_BOOTLOADER_NUM_PIN_FACTORY_RESET`, `CONFIG_BOOTLOADER_DATA_FACTORY_RESET`, `CONFIG_BOOTLOADER_OTA_DATA_ERASE`; `CONFIG_BOOTLOADER_APP_TEST` with `CONFIG_BOOTLOADER_NUM_PIN_APP_TEST`, `CONFIG_BOOTLOADER_APP_TEST_PIN_LEVEL`, `CONFIG_BOOTLOADER_HOLD_TIME_GPIO` default 5 s; this picks `TEST_APP_INDEX`), only when the reset reason is not deep sleep, then `bootloader_utility_load_boot_image(&bs, boot_index)`. Docs: https://docs.espressif.com/projects/esp-idf/en/v5.4.1/esp32s3/api-guides/bootloader.html (Customizing the bootloader, examples `custom_bootloader/bootloader_hooks` and `custom_bootloader/bootloader_override`, project dir `bootloader_components`).
- The hooks (`bootloader_before_init`, `bootloader_after_init`) cannot change the selected index. The stock GPIO options need the button held at reset and ignore the 5 s splash design.
- Recommended "picker runs every boot" mechanism: a project `bootloader_components/main` override (copy of `bootloader_start.c`, from the `bootloader_override` example) with one change in `select_partition_number`:
  1. If reset reason (`esp_rom_get_reset_reason(0)`) is deep sleep: keep the otadata choice (so Meshtastic resumes itself).
  2. Else if reason is software reset (`RESET_REASON_CORE_SW`) and a "launch token" in RTC FAST memory is valid (magic plus CRC, at a fixed address or via `bootloader_common_get_rtc_retain_mem`): clear the token, then use `bootloader_utility_get_selected_boot_partition()` (otadata).
  3. Else: boot the factory picker (`FACTORY_INDEX`).
  The picker, after the splash/menu, calls `esp_ota_set_boot_partition(mode_partition)` (or skips the write when unchanged to save otadata wear), writes the token, and calls `esp_restart()`.
  RTC FAST memory survives a software reset (not power-on). Because the bootloader consumes the token, any later reboot (power, watchdog, the mode's own `esp_restart`, BOOT button) comes back through the picker, which is intended; a PRG hold works as an explicit escape. Alternative with no custom main: in `bootloader_after_init` erase otadata unless the token is valid (writes flash every boot, less clean). Another alternative: GPIO0 held for `CONFIG_BOOTLOADER_APP_TEST` with the picker as the `test` app, but then the picker only appears on a held button.
- If a mode itself calls `esp_ota_set_boot_partition` and restarts (Meshtastic OTA to ota_1, Arduino `Update`), the token is absent, so the picker starts. The picker should look at `esp_ota_get_boot_partition()` and, if it differs from the last chosen mode, launch it immediately with no splash.
- Risks: the custom bootloader is not updatable by the apps and a bad build bricks until USB download mode (303A:1001 built-in ROM download is always available, so recoverable); bootloader size limit 0x7000 before the partition table at 0x8000 (raise `CONFIG_PARTITION_TABLE_OFFSET` if it grows; apps do not care); any firmware that writes RTC FAST at the token address between picker and bootloader is not a concern because the token is consumed on the very next boot; a firmware that erases otadata or runs `esptool` style rewrites of 0x0 to 0x10000 (rnodeconf, PlatformIO upload, Meshtastic web flasher) replaces the picker; fallback: `bootloader_utility_load_boot_image` tries other slots if the chosen one fails verification, which can start an unintended mode; verify on hardware.

## 5. Shared NVS
- Arduino core 2.0.17 `initArduino()` calls `nvs_flash_init()` on the default "nvs" label, and on `ESP_ERR_NVS_NO_FREE_PAGES` or `ESP_ERR_NVS_NEW_VERSION_FOUND` erases the first partition with subtype nvs (`esp_partition_find_first(DATA, NVS, NULL)`) and re-inits (esp32-hal-misc.c). A full or incompatible NVS therefore wipes every mode's settings. Meshtastic `factoryReset` calls `nvs_flash_erase()`.
- RNode EEPROM lives in NVS namespace "eeprom" (Arduino EEPROM lib uses `nvs_open`, no partition label). Meshtastic uses namespaces `meshtastic` and `MeshtasticOTA`; NimBLE bonds (Meshtastic and Simian both NimBLE) use the same NimBLE bond namespaces and would mix, harmless but shared pairing. Namespace names are otherwise distinct (no collision found).
- NVS format: IDF 4.4 and 5.x both write format v2 (multi-page blobs); no incompatibility known. UNVERIFIED by test.
- Separate NVS per firmware: only for code we control (our modem and Simian can use `nvs_flash_init_partition("label")`). RNode and Meshtastic use the default API with label "nvs" (Preferences/EEPROM/`nvs_open`), so unmodified upstream images cannot use another label. Mitigation: bigger shared nvs (60 KB), the three third-party users share it, tell users factory reset in Meshtastic erases RNode provisioning, or let the picker back up and restore the "eeprom" blob.
- "spiffs" label clash: RNode's console image (SPIFFS) and Meshtastic's LittleFS both default to label "spiffs". Use that one partition for Meshtastic and do not flash RNode's console image (RNode still works over USB serial and Bluetooth). If RNode's console mounts a LittleFS-formatted "spiffs" it may format it: UNVERIFIED; leave the web console disabled.

## Recommended 16 MB partition layout (0x1000000)
| Name | Type/Subtype | Offset | Size | Notes |
|---|---|---|---|---|
| bootloader | n/a | 0x0 | to 0x8000 | custom bootloader, QIO 80 MHz 16 MB |
| partition table | n/a | 0x8000 | 0x1000 | |
| nvs | data/nvs | 0x9000 | 0xF000 (60 KB) | shared; larger than default 0x5000 |
| otadata | data/ota | 0x18000 | 0x2000 | |
| picker | app/factory | 0x20000 | 0x100000 | picker, OLED and menu |
| meshtastic | app/ota_0 | 0x120000 | 0x380000 | 3.5 MB |
| meshtastic_ota | app/ota_1 | 0x4A0000 | 0xA0000 | 640 KB loader, found by subtype ota_1; keep disabled until its target is verified |
| modem | app/ota_2 | 0x540000 | 0x140000 | LFD3K-SM, 916 KB today |
| simian | app/ota_3 | 0x680000 | 0x180000 | 1.07 MB today |
| rnode | app/ota_4 | 0x800000 | 0x200000 | RNode, 2 MB as in no_ota |
| spiffs | data/spiffs | 0xA00000 | 0x200000 | Meshtastic LittleFS (label "spiffs") |
| littlefs | data/spiffs | 0xC00000 | 0x100000 | Simian marks (label "littlefs") |
| camdb | data/0x40 | 0xD00000 | 0x2F0000 | Simian camera DB, 3 MB (file is 1.99 MB now); update flash_camdb.ps1 |
| coredump | data/coredump | 0xFF0000 | 0x10000 | |

Total ends exactly at 0x1000000. Subtypes ota_0..ota_4 are contiguous (required by `esp_ota_get_next_update_partition`, which cycles by subtype number); no image should use Arduino `Update` or the IDF `esp_ota_begin` with "next partition" semantics except under picker control. Because Simian's `LittleFS` and camdb use labels, no code change is needed except the flash script offset.
